# crmshop — сайт интернет-магазина, панель управления и бот MAX

Серверная часть к Android-приложению CRM SISTEMS: витрина с карточками товаров,
регистрация клиентов по телефону, оформление заказов, панель управления и REST API,
через который то же самое видит приложение.

Написано на Go без веб-фреймворков: `net/http` + `html/template` + SQLite
(`modernc.org/sqlite` — чистый Go, без cgo). Собирается в один статический бинарь,
на сервере занимает около 4 МБ оперативной памяти.

Ничего о конкретном магазине в коде нет: название, описание, контакты, тексты
разделов, токен бота и ключ ИИ лежат в таблице `settings` и задаются из приложения.
Установка — `install.sh`, подробно в [SETUP.md](SETUP.md).

## Экраны сайта

| Адрес | Что там |
|---|---|
| `/` | Главная: обложка, категории, ходовые товары |
| `/catalog` | Каталог с фильтром по категориям и поиском |
| `/product/{id}` | Карточка товара: состав, остаток, выбор количества |
| `/cart` | Корзина (живёт в cookie, работает без регистрации) |
| `/checkout` | Оформление: ФИО, телефон, адрес, доставка, оплата |
| `/order/{id}` | Подтверждение и состав заказа |
| `/register`, `/login` | Регистрация и вход **по телефону и паролю** |
| `/profile` | Кабинет: история заказов, свои данные, смена пароля |
| `/contacts` | Контакты, доставка, оплата |

## Панель управления

`/admin` — вход по логину и паролю из `crmshop.env`.

* **Сводка** — выручка, прибыль, средний чек, новые заказы, стоимость склада,
  топ товаров, что заканчивается.
* **Заказы** — вкладки по статусам, поиск, карточка заказа со сменой статуса.
* **Товары** — полный CRUD, загрузка фотографии, наценка, публикация на витрине.
* **Склад** — правка остатков прямо в таблице, подсветка «заканчивается».
* **Клиенты** — список с суммой покупок, карточка с историей заказов и сегментом.
  В карточке — блокировка (не может войти и заказать на сайте, сессии закрываются
  сразу) и удаление (заказы остаются целыми: в них лежат снимки имени и телефона).

## Данные

`products`, `clients`, `orders`, `order_items`, `admins`, `sessions` — SQLite,
файл `/opt/crm/ИМЯ/data/shop.db`.

Поля `products` и `clients` намеренно повторяют Room-сущности приложения
(`data/entity/Product.java`, `Client.java`), чтобы их можно было синхронизировать.
Отличия: у клиента ФИО разбито на три поля (фамилия/имя/отчество) и добавлен
`password_hash`; у товара есть `published` и `image` — они нужны только витрине.

Цена и себестоимость записываются в позицию заказа **снимком** на момент покупки —
как в приложении, чтобы правка карточки товара не меняла старые отчёты.

Склад списывается в той же транзакции, что и создание заказа. При переводе заказа
в «Отменён» товар возвращается на склад, при возврате в работу — списывается снова.

## Сколько можно заказать

Покупатель набирает заказ целыми числами: кнопки «−» и «+» шагают по единице,
в поле принимаются только целые, меньше одного заказать нельзя — доставка
начинается с килограмма. Проверка серверная (`buyerQty` в `shop.go`), поэтому
её не обойти ни подделанной формой, ни ботом MAX.

Дробные количества остались у продавца: он правит состав уже оформленного
заказа, когда покупатель по телефону просит взять поменьше.

## Объединение заказов одного покупателя

Заказ с телефона, по которому уже есть **открытый** заказ (Новый, Принят,
Собирается), не заводится заново: товары дописываются в тот заказ, одинаковые
позиции по той же цене складываются, адрес и способ получения берутся из
последнего заказа, а комментарии копятся все (`merge.go`). Так продавец звонит
покупателю один раз, а не по разу на каждую корзину. Телефон сверяется
нормализованным, поэтому «8 999…» и «+7 999…» — один человек.

Выполненный и отменённый заказы не трогаются: первый — уже выручка, второй —
возвращённый на склад товар. Продажи из приложения (`source=app`) не участвуют
в объединении вовсе — это архив сделок, а не заявки.

Заказ, который успели принять или начать собирать, после дозаказа возвращается
в «Новый»: состав и сумма стали другими, а продавец подтверждал прежние. Заодно
о заказе снова напомнит уведомление в телефоне — оно живёт как раз по «Новым».

Покупатель видит на сайте (и в боте MAX) «Добавили в ваш заказ №…» вместо
«Заказ принят», чтобы номер и сумма больше корзины его не удивляли.

Старые дубли, накопившиеся до этого, сводит приложение: при обмене оно находит
открытые заказы с одинаковым телефоном и присылает их id в
`POST /api/v1/crm/orders/merge`. Остаётся самый ранний заказ (его номер
покупатель уже знает), склад при переносе не двигается — товар не исчез,
а перешёл в другой заказ.

## Учётные записи и пароли

Логин и пароль администратора, а также ключ API лежат в `/opt/crm/ИМЯ/crmshop.env`
(права 600). Чтобы сменить пароль администратора, поменяйте `SHOP_ADMIN_PASS`
и удалите строку из таблицы `admins` — при следующем запуске учётка создастся заново:

```sh
sqlite3 /opt/crm/ИМЯ/data/shop.db "DELETE FROM admins;"
systemctl restart crm-ИМЯ
```

Пароли клиентов хранятся как PBKDF2-SHA256, 120 000 итераций (`crypto/pbkdf2`
из стандартной библиотеки). Телефон приводится к виду `+7XXXXXXXXXX`, поэтому
`8 (912) 000-11-22` и `+79120001122` — один и тот же клиент.

### Покупатель забыл пароль

Ни почты, ни СМС магазин не рассылает, поэтому восстановление тут человеческое:
на странице входа под формой есть «Забыли пароль?» с телефоном магазина.
Покупатель звонит, продавец задаёт новый пароль — в карточке клиента в
приложении или в админке (блок «Забыл пароль») — и диктует его в разговоре.
Пустое поле означает «придумай сам»: сервер вернёт готовый пароль из букв и
цифр без похожих друг на друга символов, такой не переврёшь по телефону.

Старые сессии покупателя при смене пароля закрываются: если паролем
интересовался кто-то чужой, он вылетит из кабинета сразу.

## REST API для приложения

Покупатель работает по токену: `Authorization: Bearer <token>`.

```
POST /api/v1/auth/register   {phone, password, lastName, firstName, middleName, email, address}
POST /api/v1/auth/login      {phone, password}  -> {token, client}
GET  /api/v1/me
GET  /api/v1/products        ?cat=&q=
GET  /api/v1/categories
GET  /api/v1/orders          свои заказы
POST /api/v1/orders          {items:[{productId, qty}], address, comment, delivery, payMethod}
```

Раздел CRM закрыт ключом `X-API-Key` (`SHOP_API_KEY`) — через него приложение
видит то же, что админка:

```
GET  /api/v1/crm/products
POST /api/v1/crm/products       создать (id=0) или обновить товар
GET  /api/v1/crm/clients
POST /api/v1/crm/clients/save   создать/обновить клиента (archived и blocked —
                                только явными полями: без поля состояние не меняется)
POST /api/v1/crm/clients/delete удалить клиента {id} (заказы остаются)
POST /api/v1/crm/clients/password {id, password} новый пароль от кабинета;
                                пустой password — сервер придумает сам и вернёт
GET  /api/v1/crm/orders         ?status=&q=
POST /api/v1/crm/orders         продажа из приложения -> заказ на сайте
POST /api/v1/crm/orders/status  {id, status}
POST /api/v1/crm/orders/merge   {ids: [..]} свести заказы одного покупателя в один
POST /api/v1/crm/orders/item    {orderId, itemId, qty} правка состава; qty=0 убирает позицию
POST /api/v1/crm/orders/item/add {orderId, productId, qty} дозаказ
POST /api/v1/crm/orders/purge   {scope: "done"|"all"} чистка архива заказов
POST /api/v1/crm/products/photo фото товара (multipart, поле «photo») -> /photo/xxx.jpg
GET  /api/v1/crm/stats          показатели, топ товаров, что заканчивается
GET  /api/v1/crm/packed         галочки «положили» из «Сборки» — общие для всех телефонов;
                                отметки выполненных/отменённых заказов сервер убирает сам
POST /api/v1/crm/packed         {set: [..], unset: [..]} -> все отметки после правки
GET  /api/v1/crm/admin          кто администратор
POST /api/v1/crm/admin/password смена логина и пароля панели
GET  /api/v1/crm/ping           проверка адреса и ключа
```

Тексты витрины, новости и бот — тоже из приложения:

```
GET  /api/v1/crm/site           контакты, верхняя полоска, тексты страниц + все новости
POST /api/v1/crm/site           сохранить тексты (пустое поле = вернуть значение по умолчанию)
POST /api/v1/crm/news           создать (id=0) или изменить новость
POST /api/v1/crm/news/delete    {id}
GET  /api/v1/crm/bot            состояние бота MAX, маска токена, группа
POST /api/v1/crm/bot            {token?, enabled, chatId, shopUrl, callWords} — пустой token
                                означает «оставить прежний»
POST /api/v1/crm/bot/check      проверить токен у MAX
GET  /api/v1/crm/bot/chats      чаты, где состоит бот
POST /api/v1/crm/bot/menu       прислать в группу карточку с кнопками
POST /api/v1/crm/bot/announce   {newsId|text} отправить новость в группу
```

Статусы заказа: `0` Новый, `1` Принят, `2` Собирается, `3` В доставке,
`4` Выполнен, `5` Отменён.

Покупателю себестоимость и прибыль не отдаются — эти поля обнуляются в ответе.

## Сборка и выкладка

```sh
sh deploy.sh root@IP shop     # собрать, залить, обновить магазин shop
```

Или кнопкой «Обновить сервер» в приложении. Версия сервера (`crmshop -version`,
поле `version` в `/api/v1/crm/ping`) — отпечаток исходников, её подставляет сборка.

Шаблоны и стили вшиты в бинарь через `//go:embed`, отдельно копировать нечего.
Фотографии товаров лежат в `data/uploads/` и переживают обновление.

Локальный запуск:

```sh
go run . -addr 127.0.0.1:8099 -db ./data/shop.db -admin-pass пароль -insecure-cookies
```

`-insecure-cookies` нужен, потому что без HTTPS браузер не примет `Secure`-куки.

## Связка с Android-приложением

Приложение — инструмент владельца магазина. В меню появился раздел **«Сайт магазина»**:

* **Заказы с сайта** (`ui/orders/`) — список заказов покупателей, карточка заказа,
  смена статуса и звонок клиенту. Данные тянутся с сервера при каждом открытии.
* **Сайт магазина** (`ui/sync/ServerSettingsActivity`) — адрес сайта, ключ доступа,
  кнопка «Проверить связь», ручная синхронизация и переход к смене пароля админки.
* **Смена пароля админки** (`ui/sync/AdminPasswordActivity`) — меняет логин и пароль
  от `/admin` прямо с телефона. Спрашивает текущий пароль, чтобы потерянный телефон
  с ключом не открыл доступ к магазину. После смены все входы в панель сбрасываются.

Как это устроено внутри:

* `net/ServerApi.java` — обёртка над `/api/v1/crm/*` на `HttpURLConnection`,
  без новых зависимостей. Все методы блокирующие, вызываются из пула потоков
  `Repository.io()`.
* `net/SyncManager.java` — сначала выгружает на сайт товары и клиентов, заведённых
  в приложении (у них `serverId = 0`), затем забирает полный список с сайта.
  При совпадении главным считается сайт: он видит заказы покупателей и списывает
  остатки, поэтому его данные свежее.
* Записи сопоставляются по `serverId`, а если его ещё нет — по артикулу (товары)
  и телефону (клиенты). Телефон сравнивается по цифрам, поэтому `8 999…` и `+7 999…`
  считаются одним человеком и дубли не появляются.
* В Room добавлено поле `serverId` у `Product` и `Client`, у товара ещё `published`.
  Версия базы поднята до 2 с обычной миграцией — набранные на телефоне данные целы.

Первая настройка: меню → «Сайт магазина» → вписать адрес и ключ (`SHOP_API_KEY`
из `crmshop.env`) → «Проверить связь» → «Синхронизировать сейчас».

Замечание про API: `POST /api/v1/crm/products` заменяет карточку целиком, поэтому
присылать нужно все поля — пропущенные затрутся. Приложение всегда шлёт объект
полностью. Исключение — `image`: если поле не прислать вовсе (`null`), картинка
останется прежней, а пустая строка её удалит.

## Бот MAX

Внутри того же бинаря живёт бот мессенджера MAX (`maxbot*.go`). Работает длинным
опросом `botapi.max.ru`, поэтому ни webhook, ни внешнего адреса не нужно — только
исходящий интернет. Токен и настройки хранятся в таблице `settings` и задаются
из приложения, опрос перезапускается на лету.

* в личном чате: каталог по разделам с фотографиями и листанием, корзина,
  оформление с телефоном по кнопке «Отправить мой номер»; постоянному покупателю
  бот показывает прошлые имя, телефон и адрес и ждёт одного подтверждения;
* в группе: молчит, пока не позовут словом-обращением («бот», «Маруся» — задаётся
  в приложении), каталог не разворачивает, а уводит в личный чат;
* новости из приложения отправляются в группу кнопкой;
* одинаковых сообщений подряд не шлёт. Пока не было связи, нажатия копились
  у MAX, и после переподключения весь запас приходил разом — в чат подряд
  улетало несколько одинаковых приглашений. Теперь такой текст уходит один раз,
  повторы в ближайшие десять секунд пропускаются (`dupWindow` в `maxbot_flow.go`).
  Корзину и заказ это не задевает: там текст каждый раз разный.

Заказ из бота создаётся тем же кодом, что и покупка с витрины: списывает склад,
заводит клиента по телефону, помечается источником `max`.

**Ночной перезапуск** (`maxbot_restart.go`). MAX иногда перестаёт отдавать
обновления: связь есть, ошибок в журнале нет, а бот молчит до перезапуска
службы. Поэтому раз в сутки — по умолчанию в 04:00 по Москве, час задаётся в
приложении — сторож отменяет старый опрос и заводит новый, с чистым маркером и
новым http-клиентом. Сообщения, пришедшие повторно после смены маркера,
отсекает прежняя защита по `mid`, так что покупателю ничего не придёт дважды.
В приложении рядом кнопка «Перезапустить сейчас» — то же самое, но руками
(`POST /api/v1/crm/bot/restart`).

### Перехват сообщений: заявки без кнопок

По кнопкам ходят не все. Пишут одной строкой — «привезите 3 кг пельменей на
Ленина 5, 8 900 123-45-67», пишут вообще без телефона — «можно на пробу тушёнку
и кашу», а продавец пересылает такие сообщения в рабочую группу. Всё это бот
разбирает сам (`maxbot_catch.go`) и молча заводит заявку:

* **есть телефон** — ищет клиента по номеру, нового заводит сам (сегмент
  «Новый», источник `MAX`, имя из профиля MAX);
* **телефона нет, но есть слово заказа** — заявка без номера, с именем и
  @именем из MAX: продавец отвечает человеку прямо в мессенджере. Список слов
  правится в приложении (`bot.orderWords`), сравнение по началу слова;
* **пересланное сообщение** — читается как сообщение его автора, а не того, кто
  переслал: у пересланного текст лежит в `link.message.text`, а сам текст
  сообщения пустой. Именно на этом заявки терялись чаще всего;
* **человек уже писал** — сообщение дописывается в его открытую заявку (ищем по
  телефону и по его MAX, таблица `bot_leads`), вторая не появляется. Телефон,
  названный позже, дописывается в заявку, заведённую без номера.

Заявка — это обычный заказ со статусом «Новый», источником `max` и пустым
составом: сообщение целиком лежит в комментарии, состав продавец дописывает
руками в приложении.

Чего бот не трогает: свой номер из контактов магазина, номера из списка
исключений (`bot.ignorePhones`), заблокированных клиентов, собственные
сообщения и сообщения продавцов — администраторов группы. Их список бот раз в
десять минут спрашивает у MAX: продавцы пишут объявления со своим номером
(«домашняя тушёнка, звоните 8 927 …») и отвечают на вопросы, заявкой это не
является. Чтобы завести заявку от их имени, сообщение покупателя достаточно
переслать — автором считается покупатель.

Номером считается 11 цифр с 7 или 8 в начале либо 10 цифр с девятки. Номер,
слипшийся с соседним числом («Строительная 28. 89378118853»), тоже находится:
проверяются начало и конец цепочки цифр. «5 кг», «заказ на 1200» и даты
телефоном не станут.

### Догон пропущенного

Длинный опрос надёжен, пока сервис жив, но связь рвётся, а при обновлении
сервер перезапускается — сообщение может проскочить мимо. Поэтому сразу при
запуске и дальше раз в десять минут бот перечитывает последние сообщения своих
чатов (`maxbot_history.go`, `GET /messages`) и разбирает те, которых ещё не
видел. Разобранные помечаются по id сообщения в таблице `bot_seen`, поэтому
повторной заявки не будет; отметка о том, до какого времени история прочитана,
лежит в `bot.catchUpAt`. Назад бот заглядывает не дальше суток, а в самый
первый раз — на полчаса, чтобы не поднять вчерашние заказы, которые продавец
давно закрыл. В переписку догон не вмешивается: он только заводит заявки.

Перехват включён по умолчанию. Выключается ключом `bot.catchPhones` в таблице
`settings` (значение `0`) или полем `catchPhones` в `POST /api/v1/crm/bot`.

## Уборка фотографий

Каждое новое фото товара ложится отдельным файлом, старое перестаёт упоминаться
в карточке. Раз в час сервис обходит папку загрузок и удаляет файлы, на которые
не ссылается ни один товар (`photos.go`). Свежие, моложе суток, не трогает —
карточка может ещё сохраняться; фото архивного товара считается используемым.

## Удаление заказов

Один заказ удаляется из приложения (`POST /api/v1/crm/orders/delete`): долгим
нажатием по строке в «Заказах» и кнопкой в карточке отменённого. Перед
удалением сервер сохраняет заказ со всем составом в файл
`data/orders-deleted-<дата>.json`, а товар, который числился списанным,
возвращает на склад — заказа больше нет, значит и остаток за ним не числится.
У отменённого заказа склад уже вернулся при отмене, поэтому второй раз он не
двигается. Тем же путём удаляет и панель управления.

Целиком архив чистится отдельно: только выполненные заказы или все
(`POST /api/v1/crm/orders/purge`). Здесь склад не двигается — товар
покупателям уже отдан.
